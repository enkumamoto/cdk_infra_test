# Project: AWS Infrastructure with CDK, ECS, RDS, Puppet and FastAPI

This project provisions a **production-ready** infrastructure on AWS using AWS CDK (Python), integrating:

- Multi-AZ VPC with redundant NAT Gateways
- EC2 Bastion Host with Puppet and IMDSv2
- RDS Aurora PostgreSQL Serverless v2 with backup and deletion protection
- ECS Fargate with high availability and auto-scaling
- ECR with lifecycle rules
- Application Load Balancer with deletion protection
- FastAPI application with connection pooling and error handling
- Client-to-Site VPN with connection logs
- Monitoring via CloudWatch Alarms
- CI/CD Pipeline with GitHub Actions

## Infrastructure Components

### S3 (Puppet Bucket)

Bucket responsible for storing Puppet manifests and modules.

- Versioning enabled
- AWS-managed encryption
- Public access fully blocked
- Retention policy: data preserved even after stack removal
- Lifecycle: old versions expire after 90 days

### VPC

- 2 AZs
- **2 NAT Gateways** (high availability per zone)
- Public subnets (ALB, NAT)
- Private subnets with egress (ECS, RDS, Bastion)
- **VPC Flow Logs** enabled for traffic auditing

### VPN (Client-to-Site)

AWS-managed VPN for secure access to the private environment.

- Access to Bastion Host without a public IP
- Mutual certificate-based authentication
- Split tunnel enabled
- **Connection logs** in CloudWatch (3-month retention)

```mermaid

    participant Bastion as Bastion Host
    participant RDS as Aurora DB

    User->>VPN: TLS connection + certificate
    VPN->>Bastion: Private access (SSH)
    VPN->>RDS: PostgreSQL access
    Bastion->>RDS: Query
```

### Bastion Host (EC2)

Private EC2 instance used for administrative access.

- Type: `t3.small`
- **IMDSv2 required** (SSRF protection)
- Access via AWS SSM (no public port exposure)
- SSH allowed only from the VPN security group

**Automatic initialisation:**

```bash
aws s3 sync s3://<bucket>/puppet /opt/puppet
puppet apply /opt/puppet/manifests/site.pp
```

### RDS Aurora PostgreSQL Serverless v2

| Configuration | Value |
|---|---|
| Engine | Aurora PostgreSQL 14 |
| Minimum capacity | 0.5 ACU |
| Maximum capacity | 8 ACU |
| Backup | 7-day retention |
| Deletion protection | Enabled |
| Stack removal | Snapshot preserved |
| Enhanced Monitoring | 60s interval |
| Exported logs | PostgreSQL → CloudWatch |
| Encryption | Enabled |
| Credentials | Generated by Secrets Manager |

### ECR (Elastic Container Registry)

- Vulnerability scan on every push
- Retention policy: images preserved after stack removal
- Lifecycle rules:
  - Untagged images removed after 1 day
  - Maximum of 10 images per repository

### ECS Fargate

Runs the FastAPI application with high availability.

| Configuration | Value |
|---|---|
| CPU per task | 512 units (0.5 vCPU) |
| Memory per task | 1024 MiB |
| Desired tasks | 2 (minimum) |
| Auto-scaling | min=2, max=10 |
| CPU scaling | target 70% |
| Memory scaling | target 80% |
| Circuit breaker | Enabled with automatic rollback |
| Container Insights | Enabled |
| Container health check | `GET /health` every 30s |

**Separate IAM roles:**
- **Execution Role**: ECR image pull + secret injection (principle of least privilege)
- **Task Role**: CloudWatch logs write only

**Injected variables:**

| Variable | Source |
|---|---|
| `DB_NAME` | Environment variable |
| `DB_HOST` | Environment variable |
| `DB_USER` | Secrets Manager |
| `DB_PASSWORD` | Secrets Manager |

### Application Load Balancer (ALB)

- Port: 80
- Routes requests to ECS
- Health check: `GET /health` (threshold: 2 healthy / 3 unhealthy)
- Deregistration delay: 30s
- **Deletion protection** enabled

### CloudWatch Alarms

| Alarm | Threshold | Periods |
|---|---|---|
| ECS CPU | > 85% | 3 of 3 |
| ECS Memory | > 90% | 3 of 3 |
| ALB Response Time | > 2s | 2 of 2 |

## FastAPI Application

**Location:** `app_fastapi/`

**Endpoints:**

| Method | Path | Description |
|---|---|---|
| GET | `/health` | Health check with real database connectivity validation |
| POST | `/items` | Insert an item (JSON body: `{"name": "..."}`) |
| GET | `/items` | List items (query param: `limit`, default 50) |

**Production features:**

- Connection pool (`ThreadedConnectionPool`, min=1, max=10)
- Error handling with transaction rollback
- Structured logging
- Input validation via Pydantic
- Table schema created automatically on startup
- Health check validates real database connectivity

**Usage examples:**

```bash
# Health check
curl http://<ALB-DNS>/health

# Create item
curl -X POST http://<ALB-DNS>/items \
  -H "Content-Type: application/json" \
  -d '{"name": "my-item"}'

# List items
curl "http://<ALB-DNS>/items?limit=10"
```

## GitHub Actions (Workflows)

### Infra Deploy (`infra-deploy.yml`)

Triggered by push to `cdk_infra_test/`, `app.py`, `requirements.txt` or `cdk.json`.

```
Checkout → AWS OIDC Auth → cdk synth → cdk deploy
```

### App Build & Push (`app-build-push.yml`)

Triggered by push to `app_fastapi/`.

```
Checkout → AWS OIDC Auth → ECR URI from CloudFormation
→ Docker build → Tag with git SHA + latest
→ Push ECR → ECS force deploy → Wait for stabilisation
```

- ECR URI fetched dynamically from CloudFormation outputs (no hardcoding)
- Image tagged with `git SHA` for traceability and `latest` for convenience
- `aws ecs wait services-stable` ensures the deployment stabilised before reporting success

### Puppet Sync (`puppet-sync.yml`)

Triggered by push to `puppet/`.

```
Checkout → AWS OIDC Auth → S3 sync → Reboot Bastion
```

## How to Execute

1. **Install dependencies**

   ```bash
   pip install -r requirements.txt
   npm install -g aws-cdk
   ```

2. **CDK Bootstrap** (first time only)

   ```bash
   cdk bootstrap
   ```

3. **Validate synthesis**

   ```bash
   cdk synth
   ```

4. **Deploy infrastructure**

   ```bash
   cdk deploy
   ```

5. **Run tests**

   ```bash
   pip install -r requirements-dev.txt
   pytest
   ```

## Best Practices Implemented

**Network and access:**
- Private subnets for all workloads
- No public IP on ECS
- Administrative access exclusively via VPN + SSM
- IMDSv2 required on Bastion
- VPC Flow Logs enabled

**Database:**
- Credentials managed by Secrets Manager
- Deletion protection enabled
- 7-day backup retention
- Snapshot preserved on stack deletion
- Encryption at rest enabled
- Enhanced monitoring and exported logs

**Application:**
- Least-privilege IAM roles (execution role ≠ task role)
- Connection pooling for efficiency
- Circuit breaker with automatic rollback
- Auto-scaling based on real metrics

**Images:**
- Non-root user in container
- Vulnerability scanning in ECR
- Lifecycle rules to prevent image accumulation

**Traceability:**
- Images tagged with git SHA
- VPN connection logs
- CloudWatch Alarms for CPU, memory and latency

**IaC and pipeline:**
- 100% infrastructure as code (CDK)
- CI/CD with OIDC (no long-lived credentials)
- Deployment waits for ECS stabilisation
